# Persistent Case API Implementation Plan

> Execute inline using the executing-plans workflow. The user authorised continuing the previously proposed persistence/API increment; no new commit or merge is included.

**Goal:** Create, read and list scoped cases and demonstrate an audited, versioned deadline change that survives restart.

**Architecture:** FastAPI accepts typed requests and resolves a bearer token to a server-configured actor. A SQLAlchemy repository stores case snapshots, audit entries and idempotent responses in one SQLite transaction. A narrow deadline operation exercises optimistic version validation without granting arbitrary case mutation.

**Tech Stack:** Python 3.11+, Pydantic 2, FastAPI, SQLAlchemy 2, SQLite, unittest/TestClient.

**Spec:** docs/contracts.md and the conversation's approved second increment. This does not implement activation, LLM execution, evidence acceptance, readiness confirmation or sending.

## Constraints

- Keep feat/core-workflow and existing changes; no automatic commit/push.
- Authentication is required on all business routes. No default token or client supplied actor header.
- Trusted local configuration supplies token hashes, actor/client grants and approved policy versions; fail startup on missing configuration.
- Case creation sets IDs, version=1, collecting/missing/not_required and empty evidence server-side. Reject empty checklists and invalid owners/policies.
- Mutations require Idempotency-Key. Same actor/operation/key/body replays the original result; different body is 409.
- BEGIN IMMEDIATE serializes SQLite writers; compare expected_state_version before an update. Audit and response storage share the write transaction. Failed writes roll back.
- Never expose SQL errors, raw validation inputs, keys or another client's case details.
